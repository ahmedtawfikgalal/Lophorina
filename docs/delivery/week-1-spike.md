# Week 1 Spike — Runbook and Results

Goal: close ADR-001 with evidence and prove the MV3 + MediaPipe build works. See [roadmap.md](roadmap.md) for the gate.

## What the spike build contains

| Piece                    | Location                                            | Purpose                                                                                                                              |
| ------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Side Panel camera host   | `src/pages/control-panel/`, `src/camera-host/`      | Start/Stop, preview, live measurements, report export                                                                                |
| Frame-loop strategies    | `src/camera-host/pipelines.ts`                      | `worker-mstp` (MediaStreamTrackProcessor → worker) and `main-rvfc` (requestVideoFrameCallback). Neither uses `requestAnimationFrame` |
| Recognition worker       | `src/camera-host/recognition.worker.ts`             | MediaPipe off the main thread (classic worker, `importScripts`)                                                                      |
| Local MediaPipe assets   | `public/mediapipe/` (generated by `npm run assets`) | WASM + model, checksum-pinned                                                                                                        |
| One-time permission page | `src/pages/permission/`                             | Fallback if the Side Panel cannot prompt for the camera                                                                              |
| YouTube probe            | `src/adapters/youtube/content-script.ts`            | Read-only: proves the content-script entry and messaging; no commands                                                                |
| Landmark recorder        | Side Panel, spike builds only                       | Exports labeled `GestureObservation[]` for replay tests — never frames                                                               |
| Smoke test               | `scripts/smoke-extension.mjs`                       | Headless Chromium + fake camera: model loads under CSP, both strategies produce observations, no external requests                   |

## Setup

```bash
npm install
npm run build:spike      # spike build (recorder on); `npm run build` = production build
npm test                 # unit tests
npm run smoke            # automated smoke test (needs Playwright Chromium)
```

Load in Chrome: `chrome://extensions` → Developer mode → **Load unpacked** → select `dist/`. Click the toolbar icon to open the Side Panel.

## Results

### Automated smoke test — 2026-10-12

Environment: WSL2 (Linux 6.6), headless Playwright Chromium, **fake camera device** (no hands), CPU delegate, target 15 fps. The extension page ran as a tab, not as a Side Panel, so this says nothing about Side Panel behavior or background operation.

| Strategy                                | Observations/s | Inference P50 / P95 | Stalls       | Stop latency |
| --------------------------------------- | -------------- | ------------------- | ------------ | ------------ |
| Worker + MediaStreamTrackProcessor      | 13             | 75–77 / 88–92 ms    | 0 (70 s run) | ≈ 1 ms       |
| Main thread + requestVideoFrameCallback | 13             | 76–79 / 84–100 ms   | 0            | ≈ 1 ms       |

What this proves:

- The production-style MV3 build loads; the three entries (Side Panel page, service worker, content script) and the classic recognition worker are produced correctly.
- MediaPipe WASM and model load **only from bundled assets** under `script-src 'self' 'wasm-unsafe-eval'`.
- Both frame loops produce observations; stopping releases the tracks.
- **Finding:** `@mediapipe/tasks-vision` 1.1.0 contains a usage logger that POSTs task statistics (task type, running mode, OS, latency) to `https://odml.pa.googleapis.com/v1/log` every 60 s and when a task closes. No frames are sent, but it would break AC-10. The CSP directive `connect-src 'self'` blocks it: the violation appears in the console and no external request was observed in a 70 s worker run. See ADR-002.

What it does **not** prove (still open for the gate):

- Side Panel camera permission behavior (S1).
- Recognition rate while a YouTube tab is focused (S2–S4) — the core ADR-001 question.
- Real-webcam latency on the target laptop. On this machine, CPU inference (~76 ms) caps the rate at ~13 obs/s, **below the 15 obs/s AC-8 target**. Measure GPU delegate and the target hardware before changing the target.
- The browser camera indicator turning off (S5, S6).

### Manual run 1 — 2026-10-12 (Side Panel, real webcam)

Environment: Windows, Chrome 154, 16 logical cores, 16 GB RAM. Laptop model, webcam, and lighting not recorded. Reports in `spike-reports/` (git-ignored, because they contain YouTube video titles).

| Run | Frame loop  | Delegate | Duration | YouTube focused                    | Obs/s        | Inference P50 / P95 | Stalls (max gap)                     |
| --- | ----------- | -------- | -------- | ---------------------------------- | ------------ | ------------------- | ------------------------------------ |
| A   | Worker      | CPU      | 6 min    | yes, whole run; panel never hidden | 8–10, steady | 105 / 151 ms        | 1 (2.8 s, while YouTube was opening) |
| B   | Main thread | CPU      | 75 s     | yes                                | 9–10         | 101 / 113 ms        | 0                                    |
| C   | Worker      | GPU      | 51 s     | yes                                | 8.3          | 18 / 32 ms          | 0                                    |
| D   | Main thread | GPU      | 26 s     | yes                                | 8.4          | 27 / 38 ms          | 0                                    |
| E   | Worker      | CPU      | 41 s     | yes                                | 3–4.6        | **298 / 446 ms**    | 0                                    |

Findings:

1. **The Side Panel keeps recognizing while YouTube is focused.** The panel document stayed visible for the whole run, and the rate didn't drift over 6 minutes. This is the core ADR-001 question, and the answer is yes. The planned 10-minute run was cut to 6 minutes.
2. **The Side Panel cannot show the camera permission prompt** (S1). `getUserMedia` failed immediately with `NotAllowedError` while the permission state was still `prompt`. The one-time grant page worked, and later starts from the panel succeeded without a prompt. Onboarding must include this step.
3. **The frame loop had a pacing bug that halved the rate.** With GPU inference at ~18 ms, the rate still sat at 8.3/s in both frame loops. That matches a webcam delivering ~16–17 fps: a strict 66.7 ms check rejects every other 60 ms frame. Fixed with `FramePacer` (`src/camera-host/frame-pacer.ts`, regression test included). The panel now also shows camera frames/s and the frame rate the camera reports, so the next run can tell camera limits from inference limits.
4. **GPU inference is 5–6× faster than CPU** (P95 32 ms vs 151 ms). Default to the worker + GPU combination.
5. **Run E is an unexplained outlier**: CPU inference 3× slower than in run A on the same settings. Possible causes include power-saving mode or battery, thermal throttling, or another heavy tab. Repeat it before drawing conclusions.
6. The landmark recording (134 observations, unlabeled) was made during the slow run E, at about 3.4 observations/s, which is too sparse for replay tests. Re-record after the fix, with labels.

### Manual run 2 — 2026-10-12 (Side Panel, worker + GPU, after the pacing fix)

| Metric                          | Result                                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Duration                        | 10 min 56 s, YouTube focused for the whole run, panel never hidden                                         |
| Observations/s                  | average 14.9, lowest 10-second slice 14.1, highest 15.2                                                    |
| Camera frames reaching the loop | ≈ 15/s. Every delivered frame was processed                                                                |
| Inference P50 / P95             | 14.7 / 29.7 ms                                                                                             |
| Stalls / max gap                | 0 / 241 ms                                                                                                 |
| Camera settings                 | 640×480, reports 30 fps; exposure time 625 (62.5 ms), which caps real delivery at ~16 fps in this lighting |

Your observations: the camera light turned off after Stop Control (S5) and after closing the Side Panel (S6), and stayed off after reloading the extension (S7).

Conclusions:

- **Recognition is limited by the camera, not by inference or Chrome throttling.** The webcam's long exposure in indoor light delivers ~15 fps; inference uses about 30 % of the frame budget at P95. In brighter light the camera will deliver more frames, and the pacer caps processing at ~15/s.
- Run E's slow CPU numbers no longer matter for the default configuration (GPU).

**S10 finding:** on the YouTube home page the probe still found a main video (`paused`). YouTube keeps `#movie_player` in the page after you leave a video. Finding a video element therefore doesn't mean the user is on a watch page, and the adapter must check the page type itself (ADR-004 rule 7).

**S11 findings** (second recording set, `tests/replay/*-17918037…`/`*-17918038…`, all at 15 obs/s):

| Recording       | Length | Content (derived from the data, to be confirmed)                                                               |
| --------------- | ------ | -------------------------------------------------------------------------------------------------------------- |
| palm-hold       | 11.4 s | 3 deliberate holds (1.6–2.8 s) plus one short 0.5 s palm                                                       |
| swipe-left      | 18.4 s | ~6 swipes, each followed by a return stroke                                                                    |
| swipe-right     | 22.7 s | ~6–8 swipes with return strokes; less regular                                                                  |
| negative-normal | 25.9 s | Mostly a closed fist held still, with two brief open palms. Not representative of 2 minutes of normal activity |

1. **Open-palm confidence is much lower than ADR-003 assumed.** Deliberate holds scored a median of 0.53–0.61; essentially no frame reached 0.80. Brief accidental palms in the negative recording reached 0.80–0.83. A 0.80 threshold would reject real gestures and still let accidental ones through. ADR-003 is revised.
2. **Return strokes look like swipes.** They are as fast and as large, starting 0.6–1.2 s after the swipe. Suppression is mandatory and its window needs tuning.
3. **Direction and handedness:** the raw frame is not mirrored. A swipe to the user's left increases landmark x, and MediaPipe labels the user's right hand "Left".
4. **Swipes often end with the hand leaving the frame**, so tracking is lost at the end of the motion.
5. **Combined recording** (`full-2-minutes`, 110 s, labeled in `tests/replay/manifest.json`):
   - Between palm holds the hand stayed in view, so the model saw one continuous open palm for about 22 s. Release detection must not depend on the hand disappearing (ADR-003, re-arm).
   - The hand was close to the camera (40–70 % of frame height) and the wrist was at the bottom edge in about a quarter of palm-hold frames. **Corrected in Week 2:** framing does not explain the low palm scores (median 0.60 with the wrist at the edge vs 0.59 without). A "keep your hand here" guide is still useful so the hand isn't lost mid-gesture.
   - **Wind-ups:** quick moves the opposite way often came just before a swipe. ADR-003 now also covers motion _before_ a swipe.
   - Only about 6 of about 10 right swipes reach 25 % of the frame in 500 ms, and the classifier often reports `None` mid-swipe. Swipe detection must use landmarks, and the distance threshold may be too strict.
   - **The normal-activity part contained 8 natural closed fists** (score median 0.91). Fist must never be mapped to a command.

**Gate decision: PASS.** ADR-001 accepted: Side Panel camera host, worker + MediaStreamTrackProcessor frame loop, GPU delegate, one-time permission page during onboarding. S8, S10 and S11 carry into Week 2 as small checks; they don't block the gate.
